## 1. Purpose

This note is not a Black Book chapter and not a theorem surface.
It is a doctrine note.

Its purpose is to stabilize a formal interpretive bridge:
- Jungian / alchemical language remains a legitimate source of symbolic pressure;
- packet architecture remains the formal vessel of passage;

The aim is to state, with more formality than the Black Books, how symbolic material should move through the theorem factory without being either repressed or inflated.

## 2. Core doctrine

The theorem factory operates with two coupled regimes.

### 2.1 Symbolic / imaginal regime
This regime contains:
- Black Book material,
- future-pass motifs,
- Alexandria semantic associations,
- analogical pressure,
- theorem images not yet formalized,
- LLM-generated structural compressions.

This regime is generative.
It is not proof.

### 2.2 Logos / authority regime
This regime contains:
- typed packetization,
- retrieval grounding,
- Lean proof-state exposure,
- execution intent freezing,
- Lean verification,
- build verification,
- semantic audit,
- promotion decision.

This regime is authoritative.
It is not generative in the same way.

The whole doctrine is therefore:

```text
symbolic generation may propose;
logos alone may integrate.
```

## 3. Packetized transmutation

In repository terms, symbolic material is transmuted through a typed packet ladder.

Canonical packet ladder:

```text
BlackBookSource
  -> TheoremCandidatePacket
  -> RetrievalPacket
  -> ProofStatePacket
  -> ProposalPacket
  -> ExecutionIntentPacket
  -> LeanVerificationPacket
  -> BuildPacket
  -> AuditPacket
  -> PromotionDecisionPacket
```

Interpretation:
- `BlackBookSource` is prima materia.
- `TheoremCandidatePacket` is symbolic material made legally visible.
- `RetrievalPacket` is contextual orientation.
- `ProofStatePacket` is local theorem attention.
- `ProposalPacket` is executable but uncertified form.
- `ExecutionIntentPacket` is frozen intent submitted to authority.
- `LeanVerificationPacket` is first proof authority.
- `BuildPacket` is compilation authority.
- `AuditPacket` is semantic integration discipline.
- `PromotionDecisionPacket` is final acceptance into stable theorem memory.

## 7. Authority gates

The Hive’s authority gates are certifying morphisms.

### 7.1 Lean gate
Type:

```text
leanVerify : ExecutionIntentPacket -> LeanVerificationPacket
```

Meaning:
- first proof authority
- rejects symbolic or proposal-level inflation
- distinguishes executable idea from theorem-checked result

### 7.2 Build gate
Type:

```text
buildVerify : LeanVerificationPacket -> BuildPacket
```

Meaning:
- compilation authority
- verifies package/module integration surface
- does not by itself establish semantic legitimacy

### 7.3 Audit gate
Type:

```text
audit : BuildPacket -> AuditPacket
```

Meaning:
- semantic hygiene gate
- prevents compiled-but-misleading closure
- prevents shadow-owner confusion
- prevents synthetic smoke from being silently promoted

### 7.4 Promotion gate
Type:

```text
promote : AuditPacket -> PromotionDecisionPacket
```

Meaning:
- final integration decision
- distinct from proof success
- distinct from build success
- distinct from audit pass unless explicitly promoted

## 11. Replay and deadends as transmutation memory

### Replay
Replay packets store stabilized successful reductions.
Operationally they are the memory of successful form.

### Deadend
Deadend packets store failed reductions with cause classification.
Operationally they are inhibition traces: memory of where symbolic or tactical pressure failed to integrate.

Doctrine:
- replay is not mere cache; it is stabilized precedent
- deadend is not waste; it is learned resistance

### Negative antiproof

A negative antiproof is a structured witness that a proposed passage does not
close for a definite reason, at a definite authority level, in a definite
corridor.

It is not merely:
- "the tactic failed"

It records:
- what failed,
- where it failed,
- why it failed,
- which authority level refused it,
- which downstream transitions are forbidden by the failure,
- whether the failure is local to this route or claims a stronger impossibility.

Packet-level antiproof kinds include:
- `proposal_rejection`
- `lean_nonclosure`
- `build_nonintegration`
- `audit_nonpromotion`
- `owner_shadow_conflict`
- `synthetic_anchor_only`
- `environment_blocked`
- `missing_owner_theorem`

The core law is:

```text
failure of this route is not erasure of the source.
failure of this route is not proof that all routes fail.
failure of this route is reusable resistance memory.
```

In thermodynamic language:
- proofs are positive condensates;
- negative antiproofs are pressure/stiffness witnesses showing why a phase did
  not stabilize.

In Jungian language:
- they are not repression;
- they are conscious discrimination;
- the dream is preserved, but this passage is marked as non-integrating.

Expertise therefore has two conserved forms:
- fossils/replays: successful closure memory;
- deadends/negative antiproofs: structured failure memory.

The expert packet system is not the one that never fails. It is the one that
remembers why each failure was necessary.

## 12. The theorem factory workflow

A disciplined theorem-factory run therefore has this form:

1. symbolic source enters from Black Book / research / semantic reservoir
2. source is distilled into `TheoremCandidatePacket`
3. candidate is routed to the correct corridor
4. retrieval packet grounds the candidate in repo structure
5. proof-state packet localizes theorem attention
6. proposal packet expresses executable hypothesis
7. execution intent freezes what will actually be tested
8. Lean verification adjudicates theorem-level executability
9. build packet adjudicates compilation-level stability
10. audit packet adjudicates semantic legitimacy
11. promotion decision adjudicates stable theorem integration
12. fossil/replay/deadend memory preserves the result of the passage

This is the formal transmutation workflow.
