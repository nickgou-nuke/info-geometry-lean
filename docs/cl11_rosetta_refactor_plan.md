# Split `Cl(1,1)` Rosetta Map And Refactor Plan

This note records the current state of the local split `Cl(1,1)` algebraic
packet across the repository and gives a staged refactor plan for reconciling
its parallel implementations without semantic displacement and without breaking
the stable code surface.

The goal is not to erase multiplicity. The goal is to keep the multiple lawful
presentations, identify one owner/default API per lane, keep alternatives
explicit, and force downstream modules to pass through compiled bridge theorems
instead of importing competing surfaces directly.

## Immediate Preservation Rules

To refactor without losing ground and without breaking the code:

1. No raw or compiling-incomplete DIII file belongs in `Canonical/All.lean`.
2. No alternative implementation is imported directly by downstream files.
3. No new file may re-own `J`, `ε`, `K`, `u_-`, `u_+`, or the split `Cl(1,1)` seed.
4. Projectors remain upstairs; downstairs only sector data and descended actions are exposed.
5. Every dual implementation needs one compiled equality/equivalence/transport bridge.
6. Every stage must preserve `InfoGeometry.Canonical.All` and direct leaf builds.

## Duplicate Preservation Protocol

When two implementations of the same packet are already present, the safe order
is mandatory:

1. Keep both implementations alive.
2. Prove the isomorphism/equality/transport bridge.
3. Route downstream users through the canonical owner or the bridge.
4. Migrate consumers file by file.
5. Only after migration is complete, demote, quarantine, or remove the duplicate.

This lane therefore follows one short law:

**bridge first, reroute second, removal last.**

## Refactor Plan

### Stage 0. Preserve the stable umbrella

- Keep `RealBdGDIIIAtom.lean` out of `Canonical/All.lean` until it compiles.
- Keep `Physics/DIIISymmetryAtom.lean` and `SuperchargeRoleMapAlt.lean` quarantined.
- Do not widen the authoritative umbrella while the DIII lane is unstable.

### Stage 1. Freeze the Rosetta map

- Treat this document as the current packet map.
- Use the six-register classification above when touching any file in this lane.
- Require every new theorem surface to declare whether it is owner, translator,
  coherence, or capstone.

### Stage 2. Normalize the local APIs

- Keep the ordinary exported names on the canonical owners.
- Keep alternatives behind explicit `Alt`-style names.
- Route downstream code through:
  - `SplitQ11*` on the abstract side,
  - `RealSplitClifford` on the doubled realization side,
  - `SplitCliffordHead*` on the Bott/tensor side,
  - `Supercharge*` closure files on the operatorial side.

### Stage 3. De-quarantine the projective coherence lane

- Finish linter cleanup for `ProjectiveSplitQ11Realization.lean`.
- Keep the distinguished vacuum explicit rather than silently collapsing it into
  standard projectivization.
- Stabilize `ProjectiveSectorDecomposition.lean` only after its bridge role is
  strict and non-vacuous.

### Stage 4. Stabilize the DIII atom from existing owners

- Rebuild `RealBdGDIIIAtom.lean` only from:
  - `RealBdG.lean`
  - `ProjectorEquivariance.lean`
  - `SuperchargeCARCCRBridge.lean`
  - `SuperchargeCentralChargeClosure.lean`
- Do not re-own the symmetry package already implicit in those files.
- Introduce proposition wrappers if theorem packages must be composed in one theorem statement.
- Only import the DIII file into the stable umbrella after leaf and umbrella builds are green.

### Stage 5. Reroute downstream consumers

- Make downstream DIII/topological files depend on the DIII bridge, not on both
  raw and canonical symmetry lanes.
- Make projector/anomaly files depend on `ProjectorEquivariance`, not on ad hoc
  local sector-swap restatements.
- Make topological/central-charge files depend on
  `SuperchargeCentralChargeClosure`, not on separate local restatements.

### Stage 6. Deprecate or demote wrappers

- Preserve old public theorem names with aliases where necessary.
- Demote purely rhetorical or duplicative surfaces to docs or quarantine rather
  than keeping them as competing pseudo-owners.
- Keep explicit alternative files only when they serve the dual-implementation law.
