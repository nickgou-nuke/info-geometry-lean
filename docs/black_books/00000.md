Track it with a **semantic audit layer** over Lean, not just by checking whether Lean accepts the proof. Lean’s kernel checks proof terms, but it does not decide whether a formal statement matches the advertised informal claim. The Lean reference explicitly distinguishes “does the theorem have a valid proof” from “what does the theorem statement mean,” and notes that kernel acceptance assumes the theorem statement corresponds to its intended meaning. ([Lean Language][1])

The reliable approach is to export facts about every declaration, compute “hollowness” signals, and make CI reject inflated declarations under strict attributes such as `@[capstone]`, `@[closure_ready]`, or your `strict_theorem`.

## 1. Track three ledgers per theorem

For each theorem, export three things:

```text
advertised layer:
  name, namespace, docstring, attributes, module path

formal layer:
  full type, unfolded conclusion, hypotheses, conclusion head,
  symbols in hypotheses, symbols in conclusion

proof layer:
  proof dependencies, used hypotheses, axioms, proof-shape,
  dead lets, local rewrites, theorem calls
```

A theorem becomes suspicious when these three layers disagree.

For example:

```lean
theorem topologicalBekensteinBound_of_connesCocycle ...
    (hCocycle : IsConnesCocycle σ u)
    ...
    (h : ∀ k, trajectoryRNBarrier n T k =
      |CocycleEntropyPotential σ u hBridge (k + 1)
        - CocycleEntropyPotential σ u hBridge k|) :
    TopologicalBekensteinBound n T :=
  fun _ _ _ _ _ _ _ _ _ _ h k =>
    h k ▸ abs_nonneg _
```

The advertised layer says Connes/Bekenstein/cocycle. The formal conclusion is only nonnegativity of a barrier. The proof layer uses `abs_nonneg` and the assumed equality, not the cocycle law. That mismatch is what you want to detect.

## 2. Export a declaration fact table

Create a JSONL artifact like:

```json
{
  "schemaVersion": 1,
  "name": "InfoGeometry.Canonical.BekensteinBound.topologicalBekensteinBound_of_connesCocycle",
  "module": "InfoGeometry.Canonical.BekensteinBound",
  "kind": "theorem",
  "attrs": ["closure_ready", "rep_depth", "capstone"],
  "docTokens": ["Cocycle", "Entropy", "Bekenstein", "Connes"],
  "nameTokens": ["topological", "Bekenstein", "Bound", "Connes", "Cocycle"],
  "typePP": "...",
  "conclusionHead": "TopologicalBekensteinBound",
  "unfoldedConclusionPP": "∀ k : Nat, 0 ≤ trajectoryRNBarrier n T k",
  "hypotheses": [
    {"name": "hCocycle", "head": "IsConnesCocycle", "usedInProof": false},
    {"name": "hBridge", "head": "ScalarCocycleBridge", "usedInProof": true},
    {"name": "h", "head": "forall_eq_abs_increment", "usedInProof": true}
  ],
  "proofDeps": ["abs_nonneg"],
  "axioms": [],
  "proofShape": ["rewrite_by_assumption", "abs_nonneg"],
  "deadLets": [],
  "localSupportScore": 1,
  "remoteSupportScore": 0
}
```

Lean already supports auditing axiom dependencies: `#print axioms` reports axioms used by a theorem and its dependencies, and Lean’s documentation notes that `sorry` and incomplete proofs are elaborated to axioms that can be detected this way. ([Lean Language][1])

So your first hard gate should be:

```text
Reject if theorem depends on sorryAx or unexpected custom axioms.
```

But that only catches unproved material. It does not catch hollow-but-valid statements. For that, you need the next layer.

## 3. Normalize theorem statements

For every declaration, decompose the type into:

```text
binders / hypotheses / conclusion
```

For example:

```lean
∀ (n : Nat) (T : SinkhornTrajectory n),
  TopologicalBekensteinBound n T
```

becomes:

```json
{
  "binders": [
    {"name": "n", "type": "Nat"},
    {"name": "T", "type": "SinkhornTrajectory n"}
  ],
  "premises": [],
  "conclusion": "TopologicalBekensteinBound n T"
}
```

Then unfold only project-level semantic wrappers, not all of mathlib:

```lean
def TopologicalBekensteinBound (T : SinkhornTrajectory n) : Prop :=
  ∀ k : Nat, 0 ≤ trajectoryRNBarrier n T k
```

So the analyzer records:

```text
declared conclusion:
  TopologicalBekensteinBound n T

unfolded project conclusion:
  ∀ k : Nat, 0 ≤ trajectoryRNBarrier n T k
```

This is essential. The name `TopologicalBekensteinBound` sounds strong; the unfolded conclusion is just nonnegativity.

Use a whitelist of definitions to unfold:

```python
UNFOLD_FOR_AUDIT = {
    "TopologicalBekensteinBound",
    "CocycleEntropyPotential",
    "TomitaCocycleEntropyPotential",
    "CocycleGeneratorLift",
    "CasiniIncrementBridge",
}
```

Do not blindly unfold everything. You want controlled semantic expansion.

## 4. Detect hollow proof mechanisms

Use specific detectors rather than one vague “math meaningless” label.

### Detector A: conclusion already known

Flag theorem `B` if there exists earlier theorem `A` such that:

```text
A.conclusion unifies with B.conclusion
and A.requires strictly fewer advertised hypotheses than B
```

In your file:

```lean
topologicalBekensteinBound_of_sinkhornTrajectory :
  ∀ (n : Nat) (T : SinkhornTrajectory n),
    TopologicalBekensteinBound n T
```

makes later theorems suspicious:

```lean
topologicalBekensteinBound_of_connesCocycle_generatorLift
topologicalBekensteinBound_of_connesCocycle_natMatch
topologicalBekensteinBound_of_tomitaConnesCocycle_casiniIncrement
...
```

because they prove the same conclusion with extra Connes/Tomita/Casini assumptions.

Algorithm:

```python
def conclusion_already_known(decl, previous_theorems):
    for prev in previous_theorems:
        if unify(prev.normalized_conclusion, decl.normalized_conclusion):
            if hypothesis_set(prev) < hypothesis_set(decl):
                return {
                    "kind": "conclusionAlreadyKnown",
                    "witness": prev.name
                }
    return None
```

### Detector B: unused advertised hypothesis

Flag hypotheses whose type head appears in the theorem name/docstring but not in the proof term.

Example:

```lean
(hCocycle : IsConnesCocycle σ u)
```

If `hCocycle` is not used in the proof, but the theorem is named `_of_connesCocycle`, then this is high-signal inflation.

Algorithm:

```python
def unused_advertised_hypotheses(decl):
    defects = []
    advertised = tokens(decl.name) | tokens(decl.doc)
    for hyp in decl.hypotheses:
        if hyp.head_token in advertised and not hyp.used_in_proof:
            defects.append({
                "kind": "unusedAdvertisedHypothesis",
                "hyp": hyp.name,
                "head": hyp.head
            })
    return defects
```

### Detector C: bridge assumption carries content

This is one of the most important detectors for LLM-generated formal math.

A bridge assumption is a premise that connects two semantic layers that the theorem name claims to derive.

Examples:

```lean
hLift :
  CocycleGeneratorLift n T (CocycleEntropyPotential σ u hBridge)
```

or:

```lean
hMatch :
  ∀ k,
    CocycleEntropyPotential σ u hBridge k
      = trajectoryRNGeneratorPotential T k
```

or:

```lean
h :
  ∀ k,
    trajectoryRNBarrier n T k =
      |CocycleEntropyPotential σ u hBridge (k + 1)
        - CocycleEntropyPotential σ u hBridge k|
```

These are not harmless assumptions. They are the bridge.

A theorem named:

```lean
topologicalBekensteinBound_of_connesCocycle
```

should not assume the exact cocycle-to-barrier bridge unless the name makes that conditionality explicit.

Algorithmically, classify a hypothesis as bridge-like if it mentions symbols from both a remote layer and the target layer.

```python
REMOTE_HEADS = {
    "IsConnesCocycle",
    "ScalarCocycleBridge",
    "CocycleEntropyPotential",
    "TomitaCocycleEntropyPotential",
    "CasiniIncrementBridge",
}

TARGET_HEADS = {
    "SinkhornTrajectory",
    "trajectoryRNBarrier",
    "phaseRNGeneratorBefore",
    "trajectoryRNGeneratorPotential",
    "TopologicalBekensteinBound",
}

def is_bridge_hypothesis(hyp):
    syms = set(hyp.symbols)
    return bool(syms & REMOTE_HEADS) and bool(syms & TARGET_HEADS)
```

Then:

```python
if decl.has_attr("capstone") and any(is_bridge_hypothesis(h) for h in decl.hypotheses):
    emit("capstoneAssumesBridge")
```

This one rule would catch many fake capstones.

### Detector D: proof by absolute nonnegativity

A theorem is suspicious if its proof core is:

```lean
abs_nonneg
```

and the conclusion is a named physical/geometric bound.

This is not always wrong, but it should be demoted unless the theorem name says exactly what it proves.

Pattern:

```text
hypothesis: B k = |X|
proof: rewrite; exact abs_nonneg X
conclusion: bound-like named proposition
```

Defect:

```json
{
  "kind": "absoluteValueNonnegativityLaundering",
  "severity": 4
}
```

### Detector E: dead support

Catch this pattern:

```lean
let _hAdd : SomeImportantLaw := by
  ...
intro k
...
```

where `_hAdd` is never used.

That is proof-camouflage. The proof visually mentions a domain theorem but does not depend on it.

Algorithm:

```python
def detect_dead_lets(proof_ast):
    return [
        let.name
        for let in proof_ast.lets
        if let.name not in free_vars(let.body_after_let)
    ]
```

Emit:

```json
{
  "kind": "deadLetSupport",
  "name": "_hAdd",
  "claimedSupport": "cocycleLogPotential_add"
}
```

### Detector F: wrapper specialization only

Catch proofs that are only:

```lean
simpa [SomeAbbrev] using previous_theorem ...
```

This is often legitimate, but it is not a new capstone. It should be classified as a wrapper.

For Tomita wrappers, emit:

```json
{
  "kind": "wrapperSpecializationOnly",
  "severity": 2,
  "baseTheorem": "topologicalBekensteinBound_of_connesCocycle_generatorLift"
}
```

Do not forbid these. Just prevent them from being counted as independent mathematical evidence.

### Detector G: definition smuggling

For definitions with impressive names, unfold and classify the body.

Example:

```lean
def TopologicalBekensteinBound (T : SinkhornTrajectory n) : Prop :=
  ∀ k : Nat, 0 ≤ trajectoryRNBarrier n T k
```

The name contains `BekensteinBound`, but the body contains no entropy/energy/radius/area relation. In your project’s language, this is a “semantic compression” or “name inflation” defect.

Algorithm:

```python
def advertised_tokens_missing_from_body(defn):
    advertised = semantic_tokens(defn.name + " " + defn.doc)
    body_symbols = semantic_tokens(defn.body_symbols)
    return advertised - body_symbols
```

For scientific naming, maintain a required-symbol policy:

```python
REQUIRED_SYMBOLS_BY_NAME_TOKEN = {
    "Bekenstein": {"entropy", "energy", "radius", "bound"},
    "Connes": {"IsConnesCocycle", "cocycle"},
    "Tomita": {"modular", "Tomita", "flow"},
    "Casini": {"relativeEntropy", "monotone", "drop"},
}
```

This should not be a hard mathematical rule, but it is a useful lint warning.

## 5. Score declarations

Use a weighted score.

```python
HOLLOW_WEIGHTS = {
    "conclusionAlreadyKnown": 5,
    "capstoneAssumesBridge": 5,
    "assumedBridgeCarriesContent": 4,
    "unusedAdvertisedHypothesis": 4,
    "deadLetSupport": 4,
    "absoluteValueNonnegativityLaundering": 4,
    "definitionSmuggling": 5,
    "semanticNameInflation": 4,
    "wrapperSpecializationOnly": 2,
    "proofByRflOrTrivial": 3,
    "proofByAssumptionEcho": 4,
    "customAxiomDependency": 5,
    "sorryDependency": 5
}
```

Then classify:

```python
def hollow_grade(score):
    if score >= 9:
        return "severe_hollow"
    if score >= 5:
        return "hollow_candidate"
    if score >= 2:
        return "low_content"
    return "clean_or_unclassified"
```

A theorem can be formally valid and still receive `severe_hollow`.

## 6. Add CI gates

Use different gates for different attributes.

For ordinary lemmas, warnings are enough.

For `@[capstone]`, make the rules strict:

```text
A capstone theorem fails CI if:

1. It assumes a bridge predicate whose name contains Bridge, Lift, Match,
   Realizes, Identifies, Eq, or Increment, unless the theorem name says
   “assuming” or “of_bridge”.

2. Its conclusion is already available from a theorem with fewer hypotheses.

3. Any advertised domain hypothesis is unused in the proof.

4. Its proof core is only rfl/trivial/assumption/abs_nonneg/simp,
   unless the theorem is explicitly marked as a wrapper or simp lemma.

5. It contains dead support lets.

6. It depends on sorryAx or a non-whitelisted custom axiom.
```

Lean’s own proof validation can tell you whether a theorem is accepted, whether it depends on axioms, and whether `.olean` proof objects can be rechecked; the official validation page recommends `#print axioms` and also discusses `lean4checker` for additional CI-level checking. ([Lean Language][1]) Your hollow-theorem gate should run after those checks.

## 7. Track “support credit” instead of just dependencies

For every theorem, compute a support profile:

```json
{
  "localSupport": 7,
  "remoteSupport": 0,
  "bridgeAssumptionSupport": 5,
  "deadSupport": 3,
  "wrapperSupport": 2,
  "netMathematicalSupport": -3
}
```

A simple model:

```python
ROLE_CREDIT = {
    "uses_domain_theorem_in_proof": 4,
    "uses_definition_unfolding": 1,
    "uses_arithmetic": 1,
    "uses_abs_nonneg": 0,
    "uses_rfl": 0,
    "uses_assumption": 0,
}

DEBT = {
    "bridge_assumed": 4,
    "advertised_hyp_unused": 4,
    "conclusion_already_known": 5,
    "dead_let_support": 4,
    "wrapper_only": 2,
}
```

Then:

```python
net_support = support_credit - hollow_debt
```

A theorem with negative support should not be counted as a substantive bridge.

## 8. Prevent LLM laundering during generation

Use a generation contract. Before accepting a theorem, require the model or author to provide:

```text
1. Exact formal claim.
2. Unfolded meaning of all named predicates.
3. List of assumptions carrying the mathematical bridge.
4. Proof dependencies.
5. Explanation of why the conclusion is not already available from weaker data.
6. Whether the theorem is a wrapper, bridge theorem, endpoint, or capstone.
```

Then enforce it mechanically.

For example, require metadata:

```lean
/--
audit:
  theorem_class: bridge
  advertised_layer: ConnesCocycle
  target_layer: SinkhornTrajectory
  bridge_assumptions_allowed: false
  expected_used_hypotheses:
    - hCocycle
    - hBridge
  expected_core_dependencies:
    - cocycleLogPotential_add
    - ...
-/
```

Your analyzer checks whether the proof actually uses the expected hypotheses and dependencies.

For capstones:

```text
bridge_assumptions_allowed: false
```

For conditional bridge lemmas:

```text
bridge_assumptions_allowed: true
```

but then the theorem name must reflect that:

```lean
topologicalBekensteinBound_of_generatorLift
```

not:

```lean
topologicalBekensteinBound_of_connesCocycle
```

## 10. Concrete prevention rule set

Add these rules to your process-flow report generator or a companion Lean-audit pass:

```python
STRICT_CAPSTONE_FORBIDDEN_DEFECTS = {
    "sorryDependency",
    "customAxiomDependency",
    "capstoneAssumesBridge",
    "conclusionAlreadyKnown",
    "unusedAdvertisedHypothesis",
    "deadLetSupport",
    "absoluteValueNonnegativityLaundering",
}

def should_fail_ci(decl):
    if "capstone" in decl.attrs:
        return any(d.kind in STRICT_CAPSTONE_FORBIDDEN_DEFECTS for d in decl.defects)

    if "closure_ready" in decl.attrs:
        return any(d.kind in {"sorryDependency", "customAxiomDependency"} for d in decl.defects)

    return False
```

Then require all generated Lean to pass:

```text
lake build
#print axioms audit
hollow theorem audit
capstone gate
dependency graph audit
```

## 11. Best naming discipline

Most hollowness disappears if names are forced to be honest.

Bad:

```lean
topologicalBekensteinBound_of_connesCocycle
```

Better:

```lean
barrier_nonneg_of_barrier_eq_abs_cocycle_increment
```

Bad:

```lean
topologicalBekensteinBound_of_connesCocycle_generatorLift
```

Better:

```lean
trajectoryRNBarrier_nonneg_of_generatorLift_abs_bound
```

Bad:

```lean
topologicalBekensteinBound_of_tomitaFlowUnitConnesCocycle_casiniIncrement
```

Better:

```lean
trajectoryRNBarrier_nonneg_of_tomitaFlowUnit_casiniBridge
```

Reserve `capstone` for the theorem that actually proves the bridge, not for a theorem that assumes it.

## 12. The core algorithm

The complete algorithm is:

```text
For each declaration:

1. Export name/doc/attrs/type/proof dependencies/axioms.
2. Decompose type into hypotheses and conclusion.
3. Unfold project semantic wrappers.
4. Classify conclusion shape.
5. Classify each hypothesis:
   local data, remote data, bridge assumption, equality match, monotonicity, etc.
6. Detect which hypotheses are actually used in the proof.
7. Compute proof dependency support.
8. Search for weaker prior theorem proving the same conclusion.
9. Detect dead support and wrapper-only proofs.
10. Compare advertised tokens against formal symbols.
11. Emit defects and score.
12. Fail CI for strict/capstone declarations above threshold.
```

That prevents the central failure mode:

```text
The LLM cannot merely attach impressive words and hypotheses to a trivial
proof, because the analyzer asks whether those hypotheses were used, whether
they carry the bridge as assumptions, whether the conclusion was already known,
and whether the formal statement actually contains the advertised mathematics.
```
